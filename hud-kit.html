Factory HUD Kit

Tokens

foundation

Every panel in the kit is built from the same seven values. Get these right in the target project first — the components fall into place because they only ever reference the variables, never a literal color.

TokenValueUsed for
--bg#191713page background, behind the canvas
--panelrgba(38,35,30,.94)every floating chrome surface (hud item, zoomer, inspector, dock, tooltip)
--linergba(126,116,96,.28)hairline borders and section dividers
--ink / --ink-dim / --ink-fine#e6dfd2 / #a8a294 / #7d7869primary text / secondary / captions
--amber#e0a02cthe one accent — computed values, active states, focus

Bevel + shadow

Every panel gets the same two-part treatment: a drop shadow so it reads as floating above the canvas, and an inset "bevel" of a light top edge / dark bottom edge so it reads as stamped sheet metal rather than a flat div.

--shadow: 0 8px 26px rgba(0, 0, 0, 0.5);
--bevel:  inset 0 1px 0 rgba(214, 198, 160, 0.14),
          inset 0 -1px 0 rgba(0, 0, 0, 0.45);

/* applied together on any chrome surface */
box-shadow: var(--shadow), var(--bevel);
Port note Swap --amber for the target project's brand accent and every "computed value" and active state follows automatically — nothing else needs to change.

Layout system

chrome positioning

All seven pieces are position: fixed, floating over a full-bleed canvas — there's no shared flex/grid page shell. Two of them measure real DOM height at runtime and write it back as CSS variables so the rest of the chrome (and the camera's usable viewport) reflows around whichever panel is currently tallest.

var lastVars = {};
function setVar(name, value) {
  if (lastVars[name] === value) return;  // avoid a ResizeObserver loop
  lastVars[name] = value;
  document.documentElement.style.setProperty(name, value);
}

function measureLayout() {
  // topbar height is variable (subtitle can wrap), so push the HUD
  // clear of it instead of hard-coding an offset
  setVar('--hud-top', Math.round(topbar.getBoundingClientRect().height - 6) + 'px');

  // dock height is variable (mobile tune drawer open/closed), so the
  // zoomer and inspector on mobile know how much to clear at the bottom
  setVar('--dock-h', Math.round(dock.getBoundingClientRect().height - 12) + 'px');
}

new ResizeObserver(measureLayout).observe(document.body);

The same measured rectangle (topbar bottom, dock top, inspector width) is also fed into the camera code so the 3D/2D scene frames itself inside the space actually left uncovered by chrome, not the full window.

Tooltip

hover

A single reusable element, positioned at the pointer on every pointermove over a hoverable scene object, hidden on pointerleave. Not per-target — one div, content swapped.

Markup

<div id="tooltip" class="tooltip" hidden></div>

Style

.tooltip {
  position: fixed;
  z-index: 20;
  max-width: 280px;
  padding: 8px 10px;
  border-radius: 4px;
  background: rgba(24, 21, 17, 0.96);
  border: 1px solid var(--line-strong);
  box-shadow: var(--shadow);
  font-size: 11.5px;
  line-height: 1.5;
  color: var(--ink-dim);
  pointer-events: none;      /* never steals the hover it's reporting on */
}
.tooltip b { display: block; color: var(--amber); font-size: 12px; margin-bottom: 3px; }

Behavior

function showTooltip(x, y, target) {
  tooltip.hidden = false;
  tooltip.innerHTML = '<b>' + target.name + '</b>' + target.short;
  var r = tooltip.getBoundingClientRect();
  // clamp inside the viewport instead of letting it run off the edge
  tooltip.style.left = Math.min(x + 14, viewW - r.width - 12) + 'px';
  tooltip.style.top  = Math.min(y + 14, viewH - r.height - 12) + 'px';
}
function hideTooltip() { tooltip.hidden = true; }

Topbar

masthead

Fixed strip, transparent gradient fade rather than a solid panel, so the scene reads through behind it. Brand mark on the left, ghost-button actions on the right; the row itself has pointer-events: none so empty space in the strip doesn't block clicks on the canvas below it — only the two child groups re-enable pointer events.

.topbar {
  position: fixed; top: 0; left: 0; right: 0;
  display: flex; align-items: flex-start; justify-content: space-between;
  gap: 16px; padding: 14px 18px;
  pointer-events: none;                 /* strip itself is click-through */
  z-index: 5;
  background: linear-gradient(to bottom,
    rgba(20,18,15,.94) 0%, rgba(20,18,15,.78) 55%, rgba(20,18,15,0) 100%);
}
.brand, .top-actions { pointer-events: auto; }   /* re-enabled per group */
Responsive Below 900px the subtitle (.brand-text p) is dropped entirely and button labels shorten ("About & accuracy" → "About") rather than wrapping.

Inspector

right panel · the data one

The panel doing the most work: a scrollable right-side card that narrates whatever is currently selected, followed by a stack of independent .sec sections — a live data sheet, material-share bars, a token trail, and a station picker. Each section is a self-contained pattern you can mix and match.

The chip's color is set inline from the selected object's own color, not a fixed class — stage-chip.style.background = hexA(s.color, 0.14) — so one station-detail card can carry a different accent per station while everything else in the panel stays neutral.

A thin progress bar (.dwell) appears under the card text only while the sim is deliberately holding on something worth reading — width tied directly to a countdown value, not a CSS animation, so pausing the sim pauses the bar.

Data sheet rows — the "graph" numbers

This is the pattern behind every live number in the panel: a label/value row, with an optional calc modifier (marks a value as derived, not input) and an optional warn modifier.

function rows(list) {
  return list.map(function (r) {
    var cls = 'row' + (r[2] ? ' calc' : '') + (r[3] ? ' warn' : '');
    return '<div class="' + cls + '"><span>' + r[0] + '</span><b>' + r[1] + '</b></div>';
  }).join('');
}
// e.g. rows([['Chamber pressure', '300 bar', false], ['Exit Mach', '4.12', true]])
.sheet .row { display: flex; justify-content: space-between; align-items: baseline;
  gap: 10px; padding: 4px 7px; border-radius: 3px; font-size: 11.5px;
  background: rgba(0,0,0,.16); }
.sheet .row span { color: var(--ink-dim); }
.sheet .row b { font-family: var(--mono); color: var(--ink); font-weight: 600; }

/* a computed row gets tinted amber and a tiny ƒ mark, so it reads
   as "worked out live" rather than "typed in" at a glance */
.sheet .row.calc { background: rgba(224,160,44,.07); }
.sheet .row.calc b { color: var(--amber); }
.sheet .row.calc span::after { content: "ƒ"; font-family: var(--mono); font-size: 9px;
  color: var(--amber); opacity: .55; margin-left: 5px; }

.sheet .row.warn { background: rgba(226,101,58,.14); }
.sheet .row.warn b { color: var(--ember); }
.sheet .row.big { margin-top: 4px; padding: 7px; }     /* headline total row */
.sheet .row.big b { font-size: 14px; }
This is the "sexy numbers" part  There's no charting library involved — the whole effect is a monospace value, a color rule tied to whether the number is raw input vs. derived, and one warn state. It reads as instrumentation because of that consistent input/derived/warn vocabulary, repeated everywhere a number appears (sheet rows, HUD chips, flight telemetry).

Slider → live value binding

One helper wires every slider: write the raw value into sim state, and format the same value into the adjacent <b> label. This is the exact mechanism that lets a footer control feed the inspector's data sheet — the slider mutates shared state, the next paint cycle recomputes the sheet from it.

function bindRange(id, out, fn) {
  var input = el[id];
  var apply = function () { el[out].textContent = fn(parseFloat(input.value)); };
  input.addEventListener('input', apply);
  apply();
}
bindRange('pc', 'v-pc', function (v) { Sim.state.chamberBar = v; return (v|0) + ' bar'; });

Porting notes

applying this to another project

The target project already has equivalent panels with different names and its own data model — here's the order that gets to visual parity fastest.

1. Tokens first

Drop the seven custom properties from Tokens into the target's root stylesheet, substituting its own accent hex for --amber. Nothing else can look right until this exists.

2. The vocabulary, not the copy

Don't port English strings ("Shop", "Station", "Build") — port the structural pattern: a HUD item is always label + mono value; a sheet row is always label + value, with .calc for anything derived and .warn for anything out of range. Map the target's own field names onto that same three-state vocabulary.

3. Bars and rows are generic renderers

The rows() helper and the material-bar map function both take plain arrays/objects — they have no knowledge of rocket engines. Point them at the target project's existing data (whatever numbers its own inspector/footer already show) and the visual output is this kit's output.

4. Layout measurement, then responsive

Wire up measureLayout() / setVar() against the target's actual topbar and dock elements before touching the mobile breakpoint rules — the fixed-position math for HUD/zoomer/inspector all depends on those two variables existing first.
